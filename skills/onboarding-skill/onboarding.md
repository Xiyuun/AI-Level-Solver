# onboarding.md · 适配层生成作业指导（阶段二·七步工作流）

> 前置：`qualification-report.md` 结论=通过。契约正文见《contract.md》（唯一权威）。
> 每步有产出物与验收标准；逐步更新 `MANIFEST.json`（README 守则 3）。

## 步骤 1：定位规则代码

- 从资格报告的"规则代码定位图"出发，通读：移动执行、碰撞/阻挡、胜负判定、道具效果
- 产出物：`rule-matrix.md` 初稿（规则、源码依据、预期、状态维度、对拍样本——逐行；开发者后续逐行确认）
- 验收标准：四类规则各有定位与至少一条源码依据引用

## 步骤 2：实现七成员（契约见 contract.md §3.1）

- 四核心：`LoadLevel / GetLegalMoves / ApplyMove / IsGoal`；三辅助：`StateKey / DescribeMove / Snapshot`
- 语言与目录按 contract.md §3.4（平台当前为 C#，目录 `adapter/` + `adapter.tests/`）
- StateKey 实现须附**维度覆盖对照表**（资格报告的状态维度枚举 ↔ 键的组成部分）
- 每处推断实现打 `// REVIEW: 推断——依据…`
- 验收标准：《test-template/》通用用例骨架全部通过；纯函数/确定性/维度判别测试不豁免

## 步骤 3：写规则单元测试 + 完成 rule-matrix.md

- 通用骨架（test-template/）之外，**项目特有机制每条至少一个边界用例**（死角判定、连锁顺序、道具边界——正是 agent 易漏处）
- 用例与 rule-matrix 行互相引用（矩阵列"单元测试编号"）
- 语义歧义（"箱子进角算死吗"）→ 问人 → 写成显式用例固定，禁止跳过
- 验收标准：每条已确认语义都有对应测试；矩阵无空行

## 步骤 4：逆向关卡格式 → 格式说明书 / 输出校验器 / 机制解锁表 + 历史关卡导入

- 读关卡数据文件（JSON/二进制/ScriptableObject）逆向格式
- 产出：`format-spec.md`（给 LLM 提示词用）、`format-validator.*`（校验函数）、`mechanics-table.json`（编号范围→可用机制）
- 历史关卡**原生格式直接入库**（无转换）；导入清单进 MANIFEST
- 验收标准：校验器对全部历史关卡通过；说明书含字段表与合法值域

## 步骤 5：视觉映射初稿

- 从 prefab/资源名/颜色猜实体外观 → `visual-mapping.json`（格式见《渲染器与视觉映射规范》§3）
- 只影响预览美观不影响正确性；未知类型渲染器会灰兜底——**宁缺勿错**
- 验收标准：全部实体/格子类型都有映射或显式留白说明

## 步骤 6：玩法规则描述文档

- `game-brief.md`：自然语言规则书，供生成端提示词（目标读者是 LLM）：规则条目 + 设计要点（各难度档的实体规模建议）
- 验收标准：策划/开发者读后能判断"这书说的就是我们游戏"

## 步骤 7：配置对拍驱动

- 按《replay-spec.md》写 harness（模板见平台仓库 `harness-templates/unity-batchmode/`）
- 驱动配置 JSON（命令/参数占位/超时）写入报告并在平台向导①登记
- 无无头基建 → 走人工对拍降级（replay-spec.md §6），报告注明
- 验收标准：harness 满足执行契约四条（真实加载路径/真实输入/游戏本体状态/胜负信号）；或降级说明齐备

## 完成判据

`deliverables.md` 清单全部齐备且 MANIFEST 指纹一致 → 提交人工审核（checklist.md 13 条 + rule-matrix 逐行）→ 三道门（平台向导③⑤⑥）。任何一门红：按《验证门》§2.1 指纹失效规则重跑。
