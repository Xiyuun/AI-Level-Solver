# LevelForge 工具通用优化方案（PiggyFarm 专项之后的下一阶段）

> 背景：2026-11-08 先用 PiggyFarm 做“可展示”的专项修复（模板出题 + 质量门 + 难度阈值），
> 目标是把比赛演示跑通；本文档记录**工具本身**要怎么改，避免把 PiggyFarm 的临时方案误当成通用能力。
>
> 原则：**游戏特定逻辑留在适配层（插件）；平台/内核只提供可选接口、通用算法和验收编排。**

> **进展（2026-11-08）**：`ComposeContext` + 流水线种子派生、`ILevelComposer.WantsFewShot`、`ILevelQualityGate`
> 已作为通用能力落地；PiggyFarm 只保留模块库/槽位/质量规则/猪数解析/阈值。
> 仍待通用化：composer SDK（模块库/变异器）、rollout 难度、能力矩阵与生成门禁。


---

## 1. 先划清两条线

| | PiggyFarm 专项（已做/在做） | 工具通用（本文档） |
|---|---|---|
| 目标 | 比赛演示、这个项目可生成可求解 | 换一个玩法也能产出高质量适配层/关卡 |
| 代码位置 | `D:\temp\PiggyFarm\adapter`（插件工程） | `AI-Level-Solver` 仓库（平台/内核/契约/skill） |
| 典型改动 | 模板 composer、质量门规则、权重阈值 | 能力接口、生成流水线、通用难度模拟、验收门禁 |
| 风险 | 只对这一个游戏有效 | 改错会影响所有玩法，需要测试/版本管理 |

**不要**把 PiggyFarm 的 6 猪模块、12×19、猪类型写进内核；这些只能留在插件里。

---

## 2. 已为 PiggyFarm 做的专项修复（作为参考实现）

1. **模板出题器（ILevelComposer）**
   - 模型只输出 `{"band":1|2|3}`，几何由代码拼装；
   - 2 档：4 个 6 猪互锁模块（24 猪/24 步）；3 档：6 个模块（36 猪/36 步）；
   - 格式/重叠/脚印由代码保证，模型不再直接写 12×19 原生 JSON。
2. **生成质量门（ILevelQualityGate）**
   - 拦截“全部同朝向/独立直道/初始全可走”的规则网格；
   - 只在生成候选上生效，不拦导入的真实关卡。
3. **生成调用关思考 + token 预算**
   - `disableThinking: true`，格式失败从“正文为空”变成具体字段错误；
   - `ITokenBudgetHint` 给模板出题 1024 token。
4. **PiggyFarm 难度阈值 v2**
   - `[10, 30]`：24 步→2 档、36 步→3 档（演示用；真实校准需要 rollout/玩家数据）。
5. **few-shot 不回退原生格式**
   - 坐标制玩法没有可转换示例时，宁可不给示例，也不塞 95 猪原生 JSON（撑爆上下文、诱导照抄几何）。

实测：2 档 24 猪/24 步、3 档 36 猪/36 步，均 1 次 LLM 调用（约 1 秒）通过；此前 3 档 8 分钟失败。

## 3. 工具通用缺口

### G1. 生成能力没有“声明 + 门禁”

- 现状：适配层没实现 `ILevelComposer` 也会走“模型直接写原生 JSON”；`GameBrief` 里写“生成端暂不适用”也照样开放按钮。
- 目标：
  - 能力矩阵：`format-only` / `composer` / `template` 三档，向导③/工作台据此决定是否开放生成；
  - 后端在发起生成时校验能力，缺能力返回可操作 409，而不是让用户等失败；
  - 能力字段进入 `GameRegistration` 或独立 `IGenerationCapability`，由插件声明。

### G2. Composer 只有接口，没有通用工具箱

- 现状：每个玩法要自己写 `Compose`/`DescribeAsCoordinates`，没有共享的坐标 schema、模块库、校验器、模板变异算法。
- 目标：
  - 定义通用 `CompositionDocument`（实体 + 朝向 + 坐标 + 约束），提供序列化/校验/渲染为原生 JSON 的 SDK；
  - 提供 **模板/模块库**：适配层可注册“可平铺模块 + 出口方向 + 依赖边”，平台负责摆放/旋转/校验；
  - 提供 **真实关卡变异器**：以导入的真实关为种子，做位置/朝向/类型扰动，求解器在环筛选；比纯 LLM 摆图可靠。

### G3. 难度模型只有“解长 + 分支”

- 现状：`DifficultyModel` 固定权重；28 只独立猪=28.2 分；无法表达发现难度/容错。
- 目标（已与用户对齐）：
  - 内核 `DifficultySimulator`：R0 均匀随机、R1 贪心、R2 一步前瞻、R3 有噪最优；
  - 输出各代理胜率、死锁率、中位步数、首次成功尝试数；
  - 用 IRT/逻辑回归估计关卡难度 δ，映射 1/2/3 档；
  - 用项目原生 `difficulty` 字段（499 关）校准，档位准确率 ≥70%；
  - 只在生成验收/深度评估跑，按 levelHash 缓存，避免每次求解都跑。
- 注意：纯随机只能做 R0，不能当唯一裁判；保留解长/分支作为“执行难度”第二维。

### G4. 生成验收只有“格式 + 档位”

- 现状：格式通过就进求解；档位相等就采纳；质量门是 PiggyFarm 临时加的。
- 目标：
  - 通用质量门接口 + 内置检查（同向比例、独立直道、初始可走比例、规则网格、对称性）；
  - 结构预检在求解前：依赖深度、初始合法动作、被迫动作比例；
  - 目标档不只看 score：档位 + 结构约束 + rollout 胜率；
  - 预算分级：2s 探针 → 完整预算；不合格候选早停，不烧 30s×N。

### G5. 生成可观测性不足

- 现状：失败原因有，但“为什么这个候选被采纳/被拒”不够结构化；用户看不到质量分项。
- 目标：
  - 候选卡片展示：格式/质量/结构/求解/难度/rollout 六段结论；
  - 保存每次候选的 `qualityProfile`/`rolloutProfile`，进校准数据底座；
  - 生成运行报告可导出（用于复盘与训练）。

### G6. Skill/文档与接口不同步

- 现状：`skills/onboarding-skill/` 只要求七成员 + 门1；composer/quality/token 预算是“可选增强”，新适配层作者不知道。
- 目标：
  - `contract.md`/`deliverables.md` 增加生成能力清单与最低要求；
  - 给出 PiggyFarm 模板作为“模板出题”参考实现（通用化后）；
  - 在 `onboarding.md` 的③路径 B 里写清“要不要实现 composer、怎么验收”。

## 4. 分阶段路线图

### P0 · 收口与能力声明（1~2 天）

- 把 `ILevelComposer`/`ITokenBudgetHint`/`ILevelQualityGate` 写进契约文档与 skill；
- 平台增加能力矩阵与生成门禁（无 composer 时明确提示/禁用）；
- 生成调用统一 `disableThinking` + token 预算；
- 指标：无 composer 的玩法不再空转；格式失败率可观测。

### P1 · 通用 rollout 难度（3~5 天）

- 内核 `DifficultySimulator` + `RolloutProfile`；
- R0/R1 先上，R2 再看成本；
- 用 33 关 PiggyFarm + 499 关原生难度标签做校准实验；
- `DifficultyModel` 升 `rollout-v1`，保留旧模型可回退；
- 指标：档位准确率、生成验收耗时、人工评审“非平凡”比例。

### P2 · Composer SDK + 模板/变异器（1~2 周）

- `CompositionDocument` + 校验/渲染 SDK；
- 模块库（可平铺、带出口方向/依赖边）；
- 真实关变异器 + 求解器在环筛选；
- PiggyFarm 的模板 composer 重写为“模块库 + 变异”，去掉硬编码 6 猪模块；
- 指标：格式通过率 ≥90%、2/3 档生成成功率、重复度/单调性检测。

### P3 · 质量门与验收统一（1 周，可与 P2 并行）

- 通用质量检查器（结构/多样性/可读性）；
- 候选六段结论 + 复盘导出；
- 预算分级与早停。

---

## 5. 验收指标（工具级）

| 指标 | 现状 | 目标 |
|---|---|---|
| 生成格式通过率 | 1/3（PiggyFarm 旧） | ≥90% |
| 2 档“非平凡”人工评审 | 28 次独立点击 | ≥80% 有跨行依赖、初始可走 ≤50% |
| 3 档生成成功率/耗时 | 8 分钟失败 | p95 ≤120s 成功 |
| 难度档位 vs 原生 difficulty 准确率 | 未测 | ≥70% |
| 换玩法接入 composer 的工作量 | 每个玩法手写 | SDK + 模板 ≤2 人日 |
| 生成候选可解释性 | 只有失败类 | 六段结论 + 可导出报告 |

## 6. 边界与风险

1. **不要把 PiggyFarm 模板写进内核**：模块/地图/猪类型是游戏知识，只能在插件。
2. **rollout 不能替代真实通过率**：代理玩家是近似；有真实玩家数据后要重新校准。
3. **不要为低胜率而低胜率**：低胜率可能来自不公平/不可读；需要死锁率、可恢复性、可读性约束。
4. **难度是二维的**：发现难度（rollout）+ 执行难度（解长/操作量）；不要只优化一维。
5. **生成能力是可选能力**：格式直通类玩法（如推箱子）不强制 composer，但必须显式声明能力等级。

## 7. 建议的下一步

1. 把 PiggyFarm 专项代码（composer/quality gate/权重）作为**参考实现**归档，不直接搬进内核；
2. 先做 P0 的能力门禁 + 文档，让工具不再对“没 composer 的玩法”假装能生成；
3. 并行做 P1 rollout 原型，用 PiggyFarm 33 关 + 499 关原生标签验证；
4. 再决定 P2 composer SDK 的抽象（模块库 vs 变异器），避免过早抽象。
