# LevelForge 路径 B 接入操作手册（前端点击级）

> 适用：把「需求包」交给外部 AI 编程助手，由它产出求解器适配层插件（DLL），平台负责验收、门禁与上线。
> 依据：2026-11-08 的前端（commit `a276114` 之后）。界面文案若后续调整，以实际按钮为准。
> 对象：第一次接入的策划/开发；不需要会写代码，但需要能判断游戏规则、能操作外部 AI 助手。

---

## 0. 两条路径先分清

| | 路径 A | 路径 B |
|---|---|---|
| 谁写适配层 | 平台内模型（设置页配置） | 外部 AI 编程助手（ZCode/Cursor 等） |
| 平台给什么 | 扫描事实 + 提示词 | **需求包**（含工具仓库、契约、项目事实、验收口径） |
| 适配层交付形态 | 平台内生成并自动装载 | 外部编译出 **插件 DLL**，在③上传 |
| 质量上限 | 单次提示词 + 编译回喂 | 外部助手可读全量代码、跑测试、迭代 |
| 本文档 | 仅作对比 | **本文档全部步骤** |

两条路径的**验收是同一套**：③自动门1 + ④人工审核 + ⑤门2（或降级）+ ⑥门3/基准/转正。

---

## 1. 角色与前置

### 角色

- **你（人）**：登记项目、确认目录、判断门2适用性、审核④清单、签认基准、决定转正。
- **外部 AI 助手**：读工具仓库与游戏代码，产出资格评估、适配层工程与 DLL、六件套产物。
- **平台**：扫描事实、生成需求包、装载插件、跑门1/门3、存档证据、执行转正门禁。

### 前置条件

1. 平台已启动：仓库根目录运行 `run.cmd`（不是 `build.cmd`），默认地址 `http://localhost:5000`。
2. 工具仓库路径已自动写入：平台启动时会填 `settings.system.toolRepoRoot`；需求包用它拼 `ProjectReference` 绝对路径。
   - 若需求包显示“**未配置工具仓库路径**”：用源码版 `run.cmd` 启动，或检查设置页。
3. 外部 AI 助手能访问：
   - LevelForge 工具仓库（`skills/onboarding-skill/`、`src/LevelForge.FacadeContracts/`、`src/LevelForge.Kernel/`）；
   - 你的游戏项目目录（关卡数据 + 玩法代码）。
4. 建议先备份游戏项目；本流程只读取项目，不改游戏代码（导入关卡只写平台库）。

## 2. 总览

```
导入项目 → ① 登记（目录 + 门2适用性）
        → ② 资格评估（复制需求包 → 外部 AI 报告 → 粘贴存档）
        → ③ 上传 DLL → 检测/门1 → 产物验收 → 导入关卡
        → ④ 人工审核清单（确认 / 不适用+理由）
        → ⑤ 门2 对拍（或登记不适用 + 人工降级说明）
        → ⑥ 运行门3 → 建立基准 → 重跑至 fresh=0 → 转正上线
```

每一步完成（`done`）后，下一步才解锁；④⑤⑥需要③的适配层就绪。

## 3. 启动与导入项目

1. 启动平台后打开 `http://localhost:5000`。
2. 顶部点 **`＋ 导入项目`**。
3. 在“项目目录”填游戏工程根目录**绝对路径**，例如：
   ```
   D:\temp\PiggyFarm\piggyfarm
   ```
4. 点 **`识别并导入`**。
5. 顶部下拉框选中新导入的玩法，点 **`接入向导`**。

导入后平台会自动扫描：关卡目录候选、源码目录候选、抽样 JSON 顶层键、观察项。扫描是机器事实，不做语义判断。

---

## 4. ① 登记（关卡目录 + 代码目录 + 门2适用性）

### 4.1 关卡根目录

- 在“关卡根目录候选”里选真正的关卡数据目录：
  - 例：`Assets/Main/LevelEditor/Luban~/Datas/Levels`（499 个 JSON，numbered）
  - 候选按“像关卡”程度排序；**不要**选到 `tsconfig.json`/工具配置目录。
- 点 **`保存关卡根目录`**。
- 若候选都不对：在输入框手填绝对路径或项目内相对路径，再保存。

### 4.2 玩法代码目录

- 在“玩法代码根目录候选”里选规则承载代码目录：
  - 例：`Assets/Main/Game/Modules/ClassicMode/Script`
- 点 **`保存玩法代码目录`**。
- 这个目录会被需求包要求“全量阅读”——规则语义以代码为准，不要只给抽样。

### 4.3 门2 适用性（必须二选一）

- **不适用**（无独立游戏本体 / 暂时不做真机对拍）：
  - 选“不适用” → 点 **`登记为不适用并完成本步`**。
- **适用**（有游戏本体 + harness 可自动对拍）：
  - 选“适用” → 点 **`探测 Unity 驱动并预填`**；
  - 补全：命令（如 `Unity.exe` 绝对路径）、参数（支持占位符 `{levelFile}` `{tapeFile}` `{outputFile}`）、超时秒数；
  - 点 **`登记驱动并完成本步`**。

> 门2 适用性由①登记，**插件重新注册不会覆盖你的选择**（已修）。后续要改，回①重选。

✅ 期望：① 状态变 `done`，②解锁。

---

## 5. ② 资格评估（路径 B）

1. 在②区点 **`路径 B · 复制需求包给外部 AI 完整评估`**（复制到剪贴板）。
2. 把需求包**完整**粘贴给外部 AI 助手，要求它按包内“任务步骤”执行。
3. 外部 AI 会先产出**资格评估**，内容至少包括：
   - 资格四问（回合制 / 状态可枚举 / 规则可判定 / 持续产关）的 `yes/no/uncertain` + **证据（文件:行号）**；
   - 机制清单；
   - 适配层风险点；
   - 卫生度分级（良好/一般/纠缠）+ 工作量预估（人日区间 + 依据）。
4. 把这份报告**原文**粘贴到②下方文本框。
5. 点 **`存档并完成`**。
   - 若外部 AI 判定无法接入：可点 **`标记受阻（未提供报告）`**，并在报告里写清阻塞原因。

注意：
- ②的“开始深度分析”是**路径 A**用的；路径 B 不需要点，除非你想让平台再生成一份初稿做对照。
- ②复制的是同一份需求包；外部 AI 可以一次把报告、适配层工程、产物都做完。
- ④清单的种子来自“模板 + 项目扫描事实”；路径 B 不会自动带入外部 AI 的核对项，需要你在④手补。

✅ 期望：② 状态变 `done`，③解锁。

---

## 6. ③ 产物验收 + 门1（路径 B 核心）

### 6.1 外部 AI 必须交付什么

在③区点 **`第①步 · 复制需求包给外部编程助手`**（②已复制可跳过，同一份包），让外部 AI 按包交付：

1. **插件工程**（放在工具仓库之外）；
2. 用**绝对路径** `ProjectReference` 引用：
   - `src/LevelForge.FacadeContracts`
   - `src/LevelForge.Kernel`
3. 实现 `IGameFacade`：`Registration`、`BuiltinLevels`、`TryGetLevelId`、`FormatErrors`、`Solve`、`RunGate1Checks`、`Play`；
4. 适配器七成员 + `IExecutionProtocol` + 场景快照，组装 `AdapterBundle`；
5. 用 `ReplayEngine.RecordTape` 产出磁带（无解/未知**不要**造磁带）；
6. 门1 五项检查用 `AdapterHosting.RunAll`；
7. 难度用 `FeatureExtractor` + `DifficultyModel`；
8. **六件套产物写进 `Registration`**：规则矩阵、格式说明书、机制表、视觉映射、玩法规则书、难度权重；
9. xUnit 测试：解析/规则/非法数据/状态键/纯函数 + 至少 1 个真实关卡端到端求解（有磁带、outcome=win）；
10. 编译出 **插件 DLL**（连同非契约依赖），**不要复制** `LevelForge.Kernel.dll` / `LevelForge.FacadeContracts.dll`（会类型分裂）。

### 6.2 上传与检测

1. ③区文件选择框选 `.dll`；
2. 点 **`第②步 · 上传适配层文件`**；期望“已接收适配层文件”；
3. 点 **`第③步 · 检测并验收（自动跑门1）`**。

期望结果：
- 出现 **“适配层已接入并通过门1 ✓（玩法名 v版本）”**；
- 五项检查卡（依赖扫描 / 状态键判别 / 纯函数 / 确定性 / 内核自测）全绿；
- ③自动标记 `done`。

门1 有 ✗ 时：
- 按卡片里的 `issues` 让外部 AI 修；
- 重新编译 DLL → **重新上传 + 重新检测**，直到全绿；
- 不要绕过门1，也不要在平台源码里改适配层。

### 6.3 产物验收

适配层就绪后，③会显示 5 项产物清单：

- 视觉映射 visual-mapping
- 机制表 mechanics-table
- 玩法规则书 game-brief
- 格式说明书 format-spec
- 规则矩阵 rule-matrix

全 ✓ 才合格。缺项 = DLL 的 `Registration` 没写全，让外部 AI 补。

可展开 **`查看适配层声明的语义`** 查看规则矩阵/格式说明书原文；注意“声明语义 ≠ 实现语义”，最终以代码、试玩回放、门2 为准。

### 6.4 导入关卡

1. 在③的导入面板确认目录（默认=①保存的关卡根目录）；
2. 点 **`导入原生关卡`**；
3. 看三类结果：
   - **导入**：进入平台库；
   - **子集外跳过**：错误信息含 `v1 支持子集` 前缀（这是范围声明，正常）；
   - **校验失败**：数据/实现问题，必须修，不能混入跳过。

> 例（piggyfarm）：33 导入 / 466 子集外跳过 / 0 失败。

✅ 期望：③ `done`，④解锁。

## 7. ④ 人工审核清单

### 7.1 这一步在做什么

- 对**适配层的规则语义**做人工核对：适配层的规则与游戏本体是否一致；
- 不是“用起来顺不顺手”的体验评价；
- 每条是**可签字的断言 + 判据**；判据会写源码文件/用例/门1 检查项。

### 7.2 操作

1. 逐条读“断言 + 判据”；
2. 三选一：
   - **`已确认`**：你对照游戏本体/源码核对过，这条成立；
   - **`不适用`**：v1 不涉及（例：特殊猪/撤销/对抗模式），**必须填理由**，理由会进审计；
   - 不选 = **待确认**，不能完成本步；
3. 可 **`删除`** 不适用条目；底部输入框可 **`追加`** 项目特有断言；
4. 全部条目有终态后，点 **`保存并完成④（已确认 X / 不适用 Y / 待确认 0）`**；
5. 期望按钮下方出现 **“✓ 已保存：④已完成”**。

### 7.3 怎么核对

- 规则类（滑行/停位/离场/胜负）：读游戏源码 + 对照适配层实现/测试；有条件用同一关在“适配层预览 vs 游戏本体”各跑一遍；
- 契约/工程类（StateKey/纯函数/无引擎依赖）：看门1 报告 + 代码；
- 子集外机制：确认 `FormatErrors` 明确拒绝（错误信息带 `v1 支持子集`），并标“不适用 + 理由”。

> 全部勾“已确认”不是目标；不能证实的条目应标不适用或留待确认。

## 8. ⑤ 门2 对拍分诊

### 8.1 若①登记为“不适用”

1. 在说明框写降级依据，例：
   ```
   人工对拍 10 关：000001/000004/...，记录见 docs/manual-pairing.md
   ```
2. 点 **`确认本步`**。

### 8.2 若①登记为“适用”

⚠️ **当前前端没有“运行门2”的按钮**（只有确认本步）。门2 需要逐关调用 API（或 batch CLI）：

```bash
curl -X POST http://localhost:5000/api/games/<gameId>/gates/2/run \
  -H "Content-Type: application/json" \
  -d "{\"levelId\":\"1\"}"
```

- 建议抽 20 关；每关返回是否通过、首次分歧步、分歧详情；
- 红灯按四类分诊：
  1. 适配层规则错 → 修适配层；
  2. harness 绕过真实输入 → 修 harness；
  3. 关卡数据错位 → 修解析；
  4. 游戏本体问题 → 上报项目组；
- 跑完把结论写进说明框，再点 **`确认本步`**。

> 这是已知 UI 缺口；如果需要在页面里跑门2，需补“门2 运行面板”。

## 9. ⑥ 门3 基准 diff + 上线注册

### 9.1 运行门3

1. 点 **`运行门3（基准 diff）`**；
2. 按钮变 **`门3运行中…（Ns）`** 并禁用；下方提示“逐关求解，可能几分钟”；右下角有 toast；
3. 完成后看四区：
   - **红灯 · 阻断转正**：结论/解长相对基准变化；
   - **黄灯 · 需人判**：同结论同解长但轨迹变化；
   - **待确认 · 新关**：没有同版本基准；
   - **一致**：与基准相同。

首次运行必然全是“待确认”（没有基准），**0 红 0 黄 ≠ 回归通过**。

### 9.2 建立基准

门3 不会把自己刚跑的结果当基准（防自证）。两条路：

- **正路（推荐）**：门2 真机执行 → 逐关“确认加入基准”（工作台执行确认卡/API）；
- **降级路（仅门2不适用且你真机逐关执行通过）**：
  1. 在⑥的 **“门3 对照基准：X/N”** 面板填：
     - **签认人**（必填，进审计）；
     - **签认说明**（≥10 字，写清依据/记录位置）；
  2. 点 **`人工签认建立基准（N 关）`**；
  3. 平台会：复用当前版本运行（没有则现跑 8s）→ 写执行确认（manual-result=win）→ 落基准（引用 `confirmation:{id}`）。

⚠️ 签认是**人的声明**，不是机器验证；没真机执行过不要签。

### 9.3 重跑门3 直到可转正

1. 再点 **`运行门3（基准 diff）`**；
2. 目标：
   - **待确认 = 0**（fresh=0，后端转正门禁硬性要求）；
   - **红灯 = 0**；
   - 黄灯需逐条判断（性能/路径漂移可接受则记录理由）；
   - 一致 ≈ 全部。
3. 若仍有大量“待确认”：基准没建全，回到 9.2。

### 9.4 转正

条件：
- 六步全部 `done`；
- 门1 pass 且 `adapterHash` 与当前适配层一致；
- 门2 适用时：有 pass 记录且 hash 一致；
- 门3 最新记录非 fail、hash 一致、`fresh=0`。

满足后点 **`转正上线（production）`**：
- 后端逐项校验，不满足会返回 409 并指出缺什么；
- 通过后 `game.status = production`，⑥自动 `done`。

> **`先上试用档（trial）` 只提前上线，不完成⑥**；⑥的完成动作是转正上线。

## 10. “生产完成”的判定（证据链）

不是“能跑/门1 绿/解出几关”，而是：

| 步骤 | 要求 | 证据 |
|---|---|---|
| ① | 关卡/代码目录确认；门2 适用性登记 | 向导存档 |
| ② | 资格报告已审核存档 | step2 detail |
| ③ | 5 件产物齐全；门1 五项**零豁免**全绿 | 验证记录（绑 adapterHash） |
| ④ | 每条有终态；确认项有人对照游戏本体核对 | step4 存档 + 审计 |
| ⑤ | 门2 pass（或登记不适用 + 人工降级说明） | gate2 记录（绑 adapterHash/harnessHash） |
| ⑥ | 基准已批准；门3 最新 **0 红、fresh=0**；六步 done | gate3 记录（绑 adapterHash/kernelVer） |

补充：
- 允许“诚实未知”（资源耗尽/超预算）：如 SlidePig 转正时 75 关基准里 44 关是未知；
- 不允许“静默错”：子集外必须明确拒绝；
- **适配层换版（DLL 重新上传/重编译）后，旧门1/2/3 证据因 hash 不一致自动失效**，必须重跑对应门；转正门禁会拒绝旧证据。

## 11. 常见问题排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 需求包显示“未配置工具仓库路径” | 平台不是源码版启动，`settings.system.toolRepoRoot` 为空 | 用仓库根目录 `run.cmd` 启动后重新复制需求包 |
| 外部 AI 编译报 `MSB1009 项目文件不存在` | `ProjectReference` 用了相对路径/工作目录不对 | 改用绝对路径引用 FacadeContracts/Kernel；确认工程在仓库外 |
| 门1 依赖扫描不过 | 插件引用了 UnityEngine/Cocos 或平台 DLL | 规则层不得引用引擎；不要复制 Kernel/FacadeContracts |
| 门1 状态键判别不过 | StateKey 漏维度 | 按 rule-matrix 声明补齐位置/朝向/类型/在场集合等 |
| 导入“校验失败”很多 | 解析器未识别字段/未按子集拒绝 | 让外部 AI 修解析器；子集外错误信息加 `v1 支持子集` 前缀 |
| 门3 全是“待确认” | 还没有基准 | 走门2 执行确认或人工签认建基准 |
| 转正 409 “仍有 N 个未确认新关” | `fresh>0` | 建全基准后重跑门3 使 fresh=0 |
| 转正 409 “指纹不一致” | 换过 DLL，旧门记录不属于当前适配层 | 重跑门1（以及门2/门3，按提示） |
| 上传 DLL 返回 409/文件锁 | 平台已装载旧插件 | 停平台 → 替换插件 → 重启 → 重新检测 |
| 点“运行门3”很久没结果 | 全量逐关求解（单关 8s 上限） | 等按钮计时结束；期间不要关页面 |
